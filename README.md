# @rin-language/contract

Shared [Zod](https://zod.dev) schemas and inferred TypeScript types for the Rin API. This package is the single source of truth between the client, the server and any other consumer. It contains schemas only: no business logic, no server or client code, and no runtime dependency besides Zod.

Every object schema is strict: unknown keys are rejected. Nothing depends on the learned language (Japanese first, others later): error types, level scales and skills belong to each language's profile in the `core` configuration, and are published through `CapabilitiesResponse`.

## What it contains

| Area | Exports |
|---|---|
| Correction | `CorrectionRequest`, `CorrectionResponse`, `Edit`, `ErrorType`, `Level` |
| Server | `CapabilitiesResponse`, `LanguageCapabilities`, `LimitsResponse`, `HealthResponse`, `ApiError`, `ApiErrorCode`, `Page`, `API_VERSION` |
| User | `UserProfile`, `UserProfileUpdate`, `SkillRating` |
| Primitives | `LanguageCode`, `Id`, `IsoDateTime`, `DayKey`, `ActivityKind` |

## Install

Zod 4 is a peer dependency, so install it alongside the package:

```sh
pnpm add @rin-language/contract zod
```

## Usage

Validate all external input (HTTP bodies, model output) with these schemas, at the boundary:

```ts
import {
  CorrectionRequest,
  type CorrectionResponse,
} from "@rin-language/contract";

const request = CorrectionRequest.parse({
  text: "私は学生です",
  language: "ja",
  level: "N4",
});
```

The JSON Schema of each schema is importable too, for tools or an OpenAPI document:

```ts
import edit from "@rin-language/contract/json-schema/Edit.json" with { type: "json" };
```

## Documentation

The schemas document themselves, and everything else is generated or derived from them, so nothing is written twice.

| You want | Look at |
|---|---|
| What a field means, its rules and examples, in your IDE | The JSDoc of each export, shown on hover in `core` and any consumer. |
| The same, as data | The JSON Schemas generated by `pnpm build` in `dist/json-schema/<Name>.json`. `Page` is a factory, so it has none: convert `Page(Item)` yourself with `z.toJSONSchema`. |
| The conventions, error codes, and valid and invalid payloads | [docs/api.md](docs/api.md) |
| What changed between versions | [CHANGELOG.md](CHANGELOG.md) |

Rules that JSON Schema cannot express (non-blank strings, `start <= end`, edit ordering, uniqueness) are written in the `description` of the schema concerned.

## Key conventions

The full list is in [docs/api.md](docs/api.md). The three that cause the most mistakes:

- **Edit positions** are UTF-16 code units, the indices `String.prototype.slice` uses. There is no `correctedText`: apply the edits to the original text.
- **Size limits are not in the contract.** The server enforces them and exposes them as `LimitsResponse`; a consumer enforces them before spending any model call.
- **Read and write shapes differ.** `UserProfile` is what the server returns; a client changes its profile with `UserProfileUpdate`. Never validate a client request with `UserProfile`.

## Development

| Script | What it does |
|---|---|
| `pnpm test` | Builds, then runs the Vitest suite (including type tests and the built package) |
| `pnpm lint` | Biome lint and format check |
| `pnpm typecheck` | `tsc --noEmit` on sources and tests |
| `pnpm build` | ESM bundle and `.d.ts` into `dist/` with tsup, then one JSON Schema per schema in `dist/json-schema/` |

### Link a local copy into `core`

Link this repo into `core` instead of publishing on every change. With both repos side by side:

```sh
# in contract/
pnpm install && pnpm build

# in core/
pnpm add @rin-language/contract@link:../contract
```

After changing a schema, run `pnpm build` again in `contract/`. Before releasing `core`, switch back to the published version with `pnpm add @rin-language/contract@<version>`. Never commit a local link.

## Versioning and release

Semantic versioning, managed with [Changesets](https://github.com/changesets/changesets).

- Within a major version, changes are additive only: new optional fields, new endpoints. Breaking changes require a new major version and a new API prefix (`/v2`). In 0.x, breaking changes are allowed and documented in the changelog.
- A published version is never edited.
- Every schema change ships with a test and a changeset (`pnpm changeset`), and is released on its own before any code uses it.

To release:

1. On a release branch from an up-to-date `main`, run `pnpm changeset version` (bumps the version and updates `CHANGELOG.md`), commit, and open a pull request. `main` is protected.
2. After the merge, from `main`: `pnpm publish --access public`.
3. Tag the merge commit: `git tag vX.Y.Z && git push origin vX.Y.Z`.
